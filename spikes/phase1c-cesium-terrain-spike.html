Phase 1c — Cesium self-hosted terrain, animated flyover

Tests whether self-hosted CesiumJS terrain (no Cesium ion — MartiniTerrainProvider from @macrostrat/cesium-martini, converting the same Terrarium raster-DEM tiles used in the earlier MapLibre spikes into quantized-mesh terrain in-browser) can handle a scripted, per-frame camera flythrough — the exact workload that broke MapLibre GL JS terrain (14–24 frames/8sec with terrain on, vs. a clean 476–482 with it off; see docs/roadmap-3d-flyover.md). No imagery/basemap layer is loaded — terrain shape is shown via Cesium's built-in sun-lighting shading only, to isolate the animated-terrain performance question the same way the Three.js spike's own scope note recommended ("no texture ... first pass, specifically to isolate the performance question").

Camera is not final (same disclaimer as Phase 1b) — a simple chase/offset camera following rattlesnake-ledge.gpx, enough motion to match the earlier MapLibre test's methodology for a fair frame-rate comparison.

Known untested assumption: CESIUM_BASE_URL is pointed at jsdelivr's copy of the npm package for Cesium's own internal Workers/Assets (unrelated to the custom Terrarium-decode worker below, which is self-contained via a Blob URL). This is the standard no-bundler pattern for CDN-loaded Cesium, but hasn't been confirmed against this exact esm.sh + jsdelivr combination — if the page below stays blank with terrain-loading errors in the status log, this is the first thing to check.
